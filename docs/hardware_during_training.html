训练时 CPU / 内存 / 磁盘 都在干什么

对应本机实测画面：CPU 33% @3.19GHz（R9 8940HX）· 内存 12.9/15.2GB（85%）· 磁盘 2% · GPU 利用率 46%。全部解释映射到本项目的真实流水线（离线预处理缓存 + num_workers=2 + pinned memory + 每 epoch 存 258MB checkpoint）。

1. 一条数据的完整旅程

2. CPU 33%：在当"指挥"而不是"工人"

角色具体工作占比特征
主进程（GIL 单线程）① Python 训练循环调度（Lightning hook 链）② 把 loss.backward() 拆成几百个 kernel 并发射进 CUDA 流 ③ 日志/进度条 ④ 每 step 与 GPU 同步点一个核心常驻忙——你看到的 3.19GHz 多半就是它
dataloader worker ×2读页缓存里的 .npy → collate（变长序列 pad 成 batch）→ pickle 序列化 → 经共享内存队列交主进程。预取下一批（prefetch_factor=3）两个核心间歇忙，与主进程重叠工作（persistent_workers 常驻，省掉每 epoch 重启的 ~秒级开销）
验证期尖峰（每 5 epoch）matplotlib 画梅尔图（CPU 光栅化）、DTW-MCD 的 numpy 循环、tensorboard 写盘短时冲高，别误判成泄漏
🔹 为什么 33% 就够不了 46% 的 GPU：GPU 每步要等"主进程发射完 + 数据到位"。串行依赖链上任何一环等待，GPU 就空转。33% CPU 配 46% GPU 说明两边的等待时间是同一份——瓶颈是链路不是某个设备的算力。

3. 内存 12.9/15.2GB（85%）：四类住户 + 一个危险的舞伴

住户大小（实测/估）性质
主进程 python.exe~2-3GBtorch 库本体 + CUDA 主机端 + 缓存的对象；私有提交内存
dataloader worker ×2~1.6GB（各 780MB）每个 worker 都要 import torch + 持有数据集引用；fork/spawn 复制的那份"底座"
页缓存（standby list）弹性，可达数 GB13000 个 .npy + json 的磁盘副本；好内存——需要时可立即让位
其他应用（浏览器/IDE/OS）视情况数 GB浏览器硬件加速还占显存，双重挤压
🔹 85% 为什么是警戒位：之前 batch64 时"共享 GPU 显存"就是把溢出的 ~1GB 塞进这份内存——85% + 1GB 会顶到换页阈值，系统开始把页缓存放出去换空间，连累 worker 读数据变慢，形成 GPU 等数据 → CPU 等内存的连锁。换 batch32+累积后两个问题一起消失，这就是"一石二鸟"的机制解释。
🔹 自查方法：任务管理器 → 详细信息 → 按内存排序，能看到多个 python.exe（主 + 2 worker）；"性能 → 内存"里"已缓存"那一栏是页缓存，不计入 12.9GB 的"使用中"。

4. 磁盘 2%：被缓存架构"退休"的部件

动作频率流量为什么感知不到
读训练数据（.npy/json）首轮 epoch~几个 GB首轮后全部驻留页缓存，后续读=纯内存命中（磁盘曲线归零）
写 checkpoint（图上尖峰来源）每 epoch 1 次258MBNVMe 顺序写 GB/s 级，0.2 秒写完；平均摊到整个 epoch ≈ 1MB/s 量级
tensorboard 事件追加持续KB 级操作系统写缓冲聚合
🔹 这正是 09-04 做的离线预处理缓存（scripts/preprocess_dataset.py）的红利：把"每步 mel 变换 + 音素化"变成"每 epoch 读现成文件"，磁盘从持续工作部件变成只负责 checkpoint 的"仓库管理员"。若删掉缓存重训一轮，你会看到磁盘曲线常年 10-30%、CPU 多一摊 mel 计算负载。

5. 流水线视角：瓶颈在哪、还有哪些杠杆

杠杆预期收益建议
加大 num_workers（2→4）batch 组装更快，GPU 等待略减内存只剩 2.3GB 余量，每个 worker ~780MB——最多再+1，否则重蹈 85% 覆辙
提高 GPU 利用率的正道—不是本机调参能解决的：需要更大的模型/批次/序列（你已在用有效 batch 64 的最大显存配置）
降低 checkpoint 频率几乎无收益（磁盘本来就不忙）不动——every_n_epochs=1 是 09-04 血泪换来的保险
关浏览器等 GPU 应用显存余量 +几百 MB值得做，也给激活留突发余量
